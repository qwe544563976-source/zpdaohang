# 判断方法蒸馏模式

> v2 升级说明：本文随拆网定案 Q19 从 cangjie-skill 搬入 book-to-judgment-navigation，作为流水线第 4 步（方法蒸馏）的完整说明；cangjie-skill 已恢复原厂，不再含本模式。文中提到的 scripts/ 与 references/ 均指本技能目录。

## 目标

从已验收正式书包或明确隔离的只读试验夹具，以及已完成的知识地图中，提炼“面对某类问题应该怎样检查”的方法候选。该模式生产判断导航的上游方法清单，不切书、不修改原文，也不直接回答用户的命盘或现实问题。

## 输入

先选择且只能选择一种输入模式：

- 正式模式：`accepted-package.json（已验收书包凭证）`；拒绝裸原文原子路径。
- 试验模式：`WORK_ORDER.json（试验工作单）`和`PILOT_STATUS.json（临时资产状态）`；必须明确禁止发布、迁移和生产执行。

随后必须同时取得：

1. 从上述输入解析出的只读 `evidence_atoms.jsonl（原文原子文件）`绝对路径；
2. 工作单声明的章节或原文原子范围；
3. `references/knowledge/`中的章节、主题和术语地图；
4. 下游能够取得的事实名称；
5. `DISTILLATION_SOURCE.json（本次蒸馏来源清单）`；
6. `pilot_only（仅供试验）`和`publishable（允许正式发布）`状态。

输入原文原子至少应有：

```text
evidence_atom_id
chapter_number
chapter_title
heading_path
content_role
exact_text
pdf_pages
citation
```

缺字段、边界或引用异常时，把问题写入 `UPSTREAM_ISSUES.json（上游问题机器记录）`，记录受影响的 `evidence_atom_id（原文原子编号）`、影响、阻塞阶段、状态和受影响方法；只有 `blocking = true` 的 P0 才停止受影响的方法，`blocking = false` 的 P1/P2 只记账，不写入方法字段，也不影响执行。`UPSTREAM_ISSUES.md（上游问题人读展示）`只能由机器记录生成。不得修改或替换原文原子。

## 真实生产入口和等待关系

每个方法批次只走这一条生产线：

```text
人工智能逐条读正式原文，输出严格结构化 JSON
→ build_methods.py 搬运编号、逐字短引和页码并装配方法
→ validate_delivery.py --require-v2 做字段、分支通电和空话检查
→ 正确／已知错误／空白三类真实检查
→ 独立人工智能只检查语义问题
→ merge_method_batch.py 把通过的批次并入全书总账
```

人工智能不得直接写 `method-recipes.json（方法机器配方）`。独立检查等待期间，本批不得并入，但没有引用本批产出的其他章节可以继续做到机器检查完成；不能让一条审计队列使整条生产线停转。审计子任务提前完成时只写固定报告，主窗口在当前批次机器检查完成前不读取、不处理该消息；到批次交界点再统一处理。

机器已经能判断的问题不再送独立检查重复判。新语义问题第一次出现时登记并修共享入口；同一家族再次出现时禁止继续逐批手修，必须先让共享代码和正反回归样本稳定抓住旧错。共享程序一旦因新的可复现 P0 解冻，独立检查必须一次覆盖完整组合矩阵：两分支、三分支、跨分支借条件、完整原文与短引，以及 `A or B`、`Either … or`、`or if/when/in`；不允许逐个漏洞解冻五轮。

## 执行顺序

### 0. 先做原文分类盘点，再找方法型原文

正式全书蒸馏不能一上来生成方法。先对工作单允许范围内的每一个
`evidence_atom_id（原文原子编号）`完成分类盘点。这里的“分类”必须拆成两列：

- `semantic_class（原文实际类型）`：这条文字本身是在教判断方法、描述条件与结果、说明取消／缓解／适用边界、给出计算方法、提供基础资料，还是案例／译注／编辑说明，或存在残缺与身份混合。
- `disposition（处理去向）`：这条文字现在是尚未生产的 `method_candidate（方法候选）`、已经进入方法步骤、只作知识资料、只作辅助材料、被上游问题阻塞、已检查但不构成方法，还是仍待审查。

`semantic_class`回答“它是什么”，`disposition`回答“现在怎么处理”；两者不能互相替代。
一条原文只能有一个最终 `disposition`，但可以被多个方法步骤引用，因此 `method_ids`
可以是多个。原文记录不得被拆开、合并、改写或重新编号。

分类完成时，明确属于判断方法、条件结果、取消边界或计算方法，但尚未生成方法配方的原文，应标记为 `method_candidate`，不能继续留在 `review_pending`，也不能提前冒充 `method_step`。`method_candidate` 不填写 `method_ids`，不能通过正式交付；方法生产完成后，它必须转为有真实引用的 `method_step`，或经复核转为 `reviewed_no_method`。

允许的 `semantic_class` 至少包括：

```text
judgment_method
condition_result
exception_boundary
calculation_rule
foundational_knowledge
case_or_commentary
unresolved_source
```

分类正式展开前，先用少量跨章节难例校准这些类别，难例至少覆盖：前后文承接、正文夹译注、残缺条件、取消条款、时间限制和计算公式。校准未完成时不得批量生成方法。

每章分类完成后还要做一次反向复查：从本章标题、正文和相邻原文重新寻找“判断顺序、成立条件、取消条件、边界和时间限制”，确认没有把真实方法误放进知识资料。`review_pending` 不得被用来掩盖不确定性；在全书盘点结束前保持未审查，盘点结束后仍未能判定的记录必须阻塞，不得强行归入知识资料。

连续编号的规则系列在生产前必须先列出完整的原文编号集合，再逐项对账。任何排除项只有在 `UPSTREAM_ISSUES.json` 中存在相同 `evidence_atom_id` 且 `blocking = true` 的问题记录时，才能标记为“上游阻塞”；没有这条记录时，不得漏掉原文，也不得自行贴“上游阻塞”标签。

### 0.1 通用内核、每书工作单和策略微调

A 类和 B 类共用同一个蒸馏内核：只读已验收的原文原子；机器负责搬运 `evidence_atom_id`、逐字短引和 PDF 页码；人工智能只负责原文最小意思、成立逻辑、取消／缓解关系和缺事实停判。机器字段或编号不能替人工智能做语义判断，人工智能也不能改写原文原子。

每本书的 `WORK_ORDER.json（本书工作单）`另行配置书籍版本、A 类或 B 类、允许范围、专题顺序、当前批次和验收要求。工作单只改变本书的组织方式，不改变通用证据、状态和执行闸门。

- A 类按稳定编号组织同型的连续规则系列；偈号或条目号只用于锁定原文集合，不能代替逐字证据。
- B 类按语义连续块、表格边界和案例边界组织专题；没有稳定偈号时不得硬套 A 类偈号，也不得把表格或案例强行改造成偈文规则。

JH8 或 RAG 缺少字段时，可以继续做候选整理和方法生产，但对应方法必须保持 `executable_in_pilot = false`；缺口只阻止执行，不得伪造“条件已满足”。普通内容批次只跑交付验证、真实正常／错误／空白三对照，以及生成报告 `audit_step_ids（机器指定的审查步骤）`列出的独立语义检查；`review_mode=full（全部检查）`时覆盖全部步骤，`review_mode=sample（抽查）`时只检查机器固定抽出的 20%。生产节奏和审计密度分开：机器检查通过且没有真实依赖的下一批可以继续生产；当前审计保持全审，连续三个批次全审且没有出现新的错误家族后才允许简单落宫批次抽审，一次性内容失误只退回本批。只有验证器发生改动时才跑验证器自测。

若新发现的验证器假通过会影响当前批次，本批考试无效，先修闸门再重考；只有明确属于当前闸门职责之外且不影响本批的边界问题，才可登记后继续。P1/P2（`blocking = false`）继续记账；原子级 P0 只隔离真正引用该原子的批次、方法和依赖，不连坐无关内容；包级 P0 仍整本书停工。已闭环批次只有在原文或共享规则真实影响它时才重检，一批失败只退回本批和真实依赖。

每批完成后用机器记录修正状态数字，不沿用估算数；合并成功时 `merge_method_batch.py` 必须自动把本批新增方法数、消化原文数和合并后剩余候选数写入整书 `PIPELINE_STATE.md`，重启只读该文件，不依赖聊天记忆。报告只写方法数、步骤数、已消化候选数、剩余候选数和机器记录路径。批次通常覆盖 40～120 个审查步骤，或一个完整专题；不得按单条原文拆批。上限仍由一次独立语义检查能够完成决定；小专题不足 40 步时，按直接依赖并入相邻专题。

审计是否完成只决定“能不能并入全书”，不决定“能不能生产下一批”。共享生成程序和验证器保持冻结；代码审计只有在真实批次被错误放行或错误拦截，并能提供批次、命令、预期与实际结果时才允许修闸门。其余疑似漏洞只登记，不修、不停产。只有包级 P0、会污染当前批次的验证器假通过，或下一批真实依赖被驳回批次时，才停止相关生产。

因此，合并队列暂时为空也不能把生产状态改成停止：只要正式书包、共享程序和下一批输入仍然健康，就继续生成下一批并完成机器检查；被拒批次留在原目录，修好后另起新目录重跑。

### 1. 先找方法型原文

只在工作单允许的原文原子范围内识别以下信号：

- 作者说明判断顺序；
- 作者要求同时检查多个对象；
- 作者说明强弱、条件、取消或例外；
- 作者说明什么时候不能采用一条结果；
- 作者给出可以重复执行的检查程序。

目录、标题和主题地图只能帮助定位。只有正文原文原子可以给步骤提供证据。

当前机械闸门把 `verse（正文偈文）`、`prose（正文论述）`和`table（正文表格）`视为可用于方法步骤的正文身份。`intro（导言）`、`note（译注或补充）`、案例、举例、译者心得和编辑意见只能作为辅助材料，不能写入通用步骤的 `evidence_refs（步骤证据列表）`。遇到未定义的新 `content_role（正文身份）`时停止该步骤并登记上游问题，不得自行猜它等同于正文。

### 2. 先建方法骨架

每个候选方法只解决一种完整判断目标，例如：完整底审、判断一颗行星、判断一个宫位、判断一个运期或判断一个专题承诺。

先写：

```text
适用问题
必须取得的事实
按情况取得的事实
步骤和依赖顺序
停止条件
```

此时不能先堆零散断语，再反向猜测方法。

如果这个方法只处理某一个宫主或宫位，方法骨架必须同时写 `target_house: 1～12`。运行时 JH8 的实际目标宫位与该数字不一致就停止；不能靠方法名称或调用者记忆默认两者已经配对。

### 2.1 写步骤前先盘点引文结构

在写任何步骤前，先逐条盘点本步骤引用的 `exact_text（原文原句）`：

- 标出所有 `AND／OR／NOT`、独立替代入口、成立条件、取消、缓解、例外和范围限定；
- 每个分支都必须进入步骤的条件树、条件组或例外关系；如果某分支只作辅助、不能形成通用规则，必须明确记录“仅辅助／不形成规则”，不能静默漏掉；
- 记录示例、特定人物、特定年龄、特定运期或特定适用对象的范围，后面写入 `applicability_scope`，不能自动扩大成通则。

这一轮只做结构盘点，不允许先凭常识补出完整公式、比例、适用对象、时间范围或结论。

盘点结果必须写成符合 `references/method-extraction.schema.json` 的纯 JSON。AI 不直接写 `method-recipes.json`；非法字段、非 JSON 文本、空话主张、未拆开的 OR、错挂阶段、补救混入风险、even if 写成 if 或指代缺少前置绑定，全部由 `scripts/build_methods.py`拒绝。

### 3. 把骨架拆成步骤

一个步骤只做一次明确检查，并具有可判断的完成标准。每个步骤分别保存：

```yaml
step_id: 稳定步骤编号
action: 本步骤做什么
applicability_scope: 本步骤只适用于什么范围
minimum_supported_claim: 原文直接支持的最小意思
produced_fact_keys: 本步骤新产生、供后续步骤使用的事实名称数组
required_fact_keys: 本步骤需要的事实名称
condition_logic: 使用 AND／OR／NOT 明确条件关系
conditional_fact_requirements: 按条件选择后才需要取得的事实组
source_status: repeated_support 或 single_explicit_source 等现有来源状态
evidence_refs:
  - evidence_atom_id: 原文原子编号
    quote: 从 exact_text 逐字截取的短引
    pdf_pages: 与原文原子完全一致的页码数组
stop_condition: 缺什么或出现什么时停止
stop_fact_keys: 与 required_fact_keys 完全一致的缺失即停字段
exception_relations: 例外、取消、缓解或限制关系及其原文编号
forbidden_extensions: 禁止从本步骤扩大出的说法
```

`produced_fact_keys`只能写本步骤真正新产生的事实，不能同时出现在本步骤输入、任何条件组输入或方法级`required_facts`、`conditional_facts`中；同一方法不能重复生产同名事实。下一步可以使用已经完成的前一步产出，当前步骤不能使用自己或未来步骤的产出。

`conditional_fact_requirements`每项必须写清`when`条件树、该分支的`required_fact_keys`和具体`stop_condition`。`when`只能用本步骤 always-required 的`required_fact_keys`或前序步骤产出；分支事实只能来自方法级`conditional_facts`或前序产出，不能用本步骤或未来产出，也不能重复 always-required 输入。主`condition_logic`可以引用 always-required、已声明的分支事实和前序产出，但不能引用当前或未来产出。

`minimum_supported_claim`必须逐句回到本步骤的某条 `quote（逐字短引）`：每个判断、公式、比例、适用对象、时间范围和结果都要有直接支持；没有直接短引的内容必须删除，不能用占星常识或其他步骤的引文补齐。`required_fact_keys`只写本步骤真正需要取得的外部输入；前序步骤已经产出的事实只能作为前序输入，本步骤新产生的事实只能写入`produced_fact_keys`，按分支才需要的事实只能写入`conditional_fact_requirements`。

一个步骤可以引用多个原文原子；不能用一个方法级宽泛引文替代逐步骤证据。
原文编号、逐字短引、非空 PDF 页码和非空停止条件少一项，该步骤都不能进入输出。
自然语言停止说明不能代替字段刹车。`stop_fact_keys`与`required_fact_keys`不一致时直接失败；`condition_logic`引用未声明、当前产出或未来产出的事实，使用未知逻辑运算，或没有覆盖本步骤 always-required 事实时直接失败；条件组缺少可选择的`when`或分支事实未在方法级声明时直接失败。

### 3.1 全书逐条登记去向

`validation/method-source-scan.json（全书方法审查清单）`必须覆盖本轮允许范围内的全部原文编号，每个编号只能出现一次，并记录以下一种去向：进入方法步骤、仅作为知识资料、案例或辅助材料、被上游问题阻塞、已检查但不构成方法、尚未审查。尚未审查的记录可以保存进度，但会阻止机械交付。

章节地图覆盖全部原文只证明“书里每条文字都有位置”，不能证明“每条文字都经过方法语义审查”。两种对账必须分开。

### 4. 记录来源状态

每个方法和步骤分别使用以下来源状态：

| 状态 | 含义 | 是否可进入执行主路 |
|---|---|---|
| `repeated_support` | 多个独立原文位置明确支持 | 核验后可以 |
| `single_explicit_source` | 只出现一次，但原文明确且身份可靠 | 核验后可以 |
| `structure_hint_only` | 只有目录、标题或结构暗示 | 不可以 |
| `synthesized_candidate` | 人工智能把多个线索组合成候选 | 拆成步骤并逐步锚定前不可以 |
| `no_source_in_scope` | 当前允许范围没有找到原文 | 不可以 |

“只出现一次”不是删除理由；“没有逐步骤证据”是停止进入执行主路的理由。

每个方法还必须保存 `workflow_history（状态变化记录）`。记录从 `pilot_candidate（试验候选）`开始，每次只允许进入下一核验阶段，或进入阻塞／拒绝；当前 `workflow_status（当前核验状态）`必须等于历史最后一项。

每个方法还必须保存：

- `fact_binding_status（排盘事实接入状态）`：只能是 `unmapped（未接入）`、`mapped（已接入）`或`unavailable（下游无法提供）`；
- `upstream_issue_ids（上游问题编号列表）`：没有开放 P0 问题时也要保存空数组；这里只能填写开放且 `blocking = true` 的问题，P1/P2 只保留在上游问题记录中；
- `dependencies（依赖方法）`：只引用同一份方法机器配方中真实存在的方法，不得形成循环。

事实未接入、依赖不可执行或存在未解决阻塞问题时，方法不得进入执行主路。

### 5. 生成四路查书计划

每个方法分别生成：

```text
support_queries：寻找直接支持
counter_queries：寻找相反、取消或缓解
boundary_queries：寻找适用条件和文本身份限制
method_queries：寻找作者怎样要求判断
```

查询词只负责告诉 RAG（原文证据检索系统）查什么，不是证据。每条查询必须保持单一目的，不能把四路混成一句。

### 6. 生成唯一方法机器真相

机器文件使用 `templates/JUDGMENT_METHOD.json.template`，全部方法集中写入 `method-recipes.json（方法机器配方）`。方法、步骤、事实、依赖、原文证据、来源状态、上游问题和执行许可只在这里写一次。唯一写入命令是：

```text
python scripts/build_methods.py --extraction <AI抽取.json> --accepted-package <正式书包凭证> --output <新批次目录>/references/navigation/method-recipes.json
```

该命令同时生成查询配方、本批原文去向、机器报告和 `validation/batch-state.json（批次状态）`。批次状态从未开工、生成中进入机检仿真；没有机器检查和三类对照记录不得进入审计中，没有独立审计记录不得并入全书。机器检查失败或独立审计发现问题时，本批必须写成 `rejected（本批失败，已经结束）`，旧目录只留证据；重新生产必须新建目录，禁止把失败目录改回进行中。新目录可以从旧批次的结构化抽取中原样搬入未被驳回的步骤，只重写被驳回步骤；随后必须重新调用生成器重建全部机器文件、派生文件、三类对照和状态，不能复制旧机器配方或旧审查结论。

审查强度由生成器决定：大运流年、多星同聚和复杂瑜伽永远逐步全审；结构单一的落宫章节只有在连续三个批次没有出现新的错误家族后才允许抽审，一次性内容失误只退回本批。抽审名单由批次名字作固定随机种子抽取 20%，不能人工换题。

人读方法、方法地图和核验状态展示必须由判断导航验证器从机器配方确定性生成并逐字核对。人读文件不得独立决定状态、事实或执行许可，也不得手改转正。

具体规则以后仍可使用 R/I/A1/A2/E/B 六段，但必须挂到某个方法步骤；案例、译注和目录不能冒充通用规则。

## 状态

试验流程固定为：

```text
pilot_candidate
→ mechanical_verified
→ independent_verified
→ shadow_passed
→ pilot_passed
```

任何阶段都可以进入 `blocked`或`rejected`。试验状态不能转成正式发布状态；正式原文原子完成后必须重新生成并重新核验。

## 禁止事项

- 不读取工作单范围外的正文进行蒸馏；
- 不读取 PDF、`book.md`或`pages.jsonl`补证据；
- 不修改、合并、拆分、重写或重新编号原文原子；
- 原文锚点只使用 `evidence_atom_id（原文证据原子永久编号）`；不输出退役地址字段；
- 不把方法摘要、查询词、案例或目录当成正式证据；
- 不让生成窗口给自己完成独立核验；
- 不把 `pilot_only = true`的产物发布或安装到正式运行环境。
- 正式原文原子到位后从知识地图开始全量重跑；不迁移临时编号、方法状态、核验或考试结论。
