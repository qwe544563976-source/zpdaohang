## 二、每批怎么跑（V3 节奏；并发办法 2026-08-22 实测改进）

规格三条死规矩：**单个 workflow 最多 3 批**（脚本里写死，超了抛错）；**agent 一律
model=opus、effort=high**；**不准边修边跑**——机检未过登记进待修清单滚动表就继续，
审计全书跑完统一安排。

### 并发上限是 per workflow，不是全局（实测，别再被它卡住）

workflow 引擎的并发上限是 `min(16, CPU核数-2)`，本机 4 核 → **一个 workflow 同时只跑 2 个
agent**。派 3 批的话第三批在队列里干等（实测等了 20 分钟）。

**上限按 workflow 独立计算**，所以要提速就**同时开多个 workflow**，每个塞 2 批：

- 2026-08-22 实测：4 个 workflow 并存 → 7 个 agent 同时在跑，`load average 0.29`（4 核）。
- 抽取是等 API 返回的 IO 活，几乎不吃 CPU，那个 `CPU-2` 上限对本场景过度保守。
- 单批实测耗时 20~38 分钟。并发 2 时剩余 45 批要 10 小时以上；并发 6~7 约 3.5 小时。

**并行度不影响总 token**：全书 2024 条原子是固定工作量，并行只决定多快烧完，不决定烧多少。
老板当初限 3 个 agent 针对的是"一批派 18 个 agent 互相重复劳动"（212 万 token 只做 39 条
原子 = 每条 5.4 万）；现在一批一个 agent 是每条约 0.86 万，没有重复劳动。

**并行度高的真实代价**：撞额度墙时在途的 agent 全被杀。因为 agent 是每写完一组就落盘自验，
损失限于最后一组（历史先例：ch28-29 的 g1 就是死前落盘保住的，重启只补缺组）。

```bash
# 1 排批：组状态由程序看目录生成，任何人不得手写
python3 distillation/prepare_batches.py --next 60
#   取 fully_extracted=false 的，label/groups/topic/note 原样抄进 workflow args

# 2 抽取：同时开 3~4 个 extract_workflow.js，每个 args.batches 放 2 批
#   agent 自己跳过已有组、只补缺的；返回必须抄机器自验真实结果（check_passed）

# 3 装配（主窗口跑脚本，零 token；agent 只交片段，绝不占 agent）
python3 distillation/make_batch.py --batch-id <ID> \
  --target distillation/bphs-97/batches/<ID> \
  --scope distillation/_local/batches/<label>/scope.json \
  --fragments distillation/_local/batches/<label>/fragments
#   机检过 → git 提交推送；未过 → 登记待修清单滚动表，目录删掉，不修，继续

# 4 agent 的 notes 落盘进 distillation/抽取员笔记_待审计.md（transcript 会丢）
# 5 回到 1，循环到 69 批抽完装配完；最后给老板发总账
```
